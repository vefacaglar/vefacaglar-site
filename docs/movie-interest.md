# Current movie Wikipedia interest

`catalog.movies.popularity.refresh` measures recent audience interest using English Wikipedia human pageviews over the latest three completed UTC days. The score is `floor((oldest + 2 * middle + 3 * latest) / 6)`. Every accepted film uses the same days, metric and denominator. Release date, age and historical recognition do not alter the measured score. Older films remain eligible when people are reading about them now. This is a bounded English Wikipedia interest chart, not a worldwide film chart or a rating.

The job first validates the latest completed day's global top-1,000 feed and maps article titles to Wikidata QIDs. This feed only selects candidates; its one-day counts are never published as rolling scores. Up to 48 known catalog films with the highest feed observations are measured through the per-article endpoint. Feed candidates always run first. The job then optionally measures up to 16 additional public catalog films released within the past year, ordered by existing Wikipedia language coverage and stable ID. This extends coverage below the global cutoff. Candidate selection does not boost scores. Films outside this bounded candidate pool remain unobserved.

Each per-article request asks for the same three-day range with `all-access/user`. This matches the human-view metric in the top feed. For example, on 2026-11-21 `XXX_(2002_film)` has 92,338 top-feed views and 92,338 per-article `user` views, while `all-agents` reports 100,269. Mixing those metrics would inflate the supplementary sample. Missing articles (404) or incomplete windows remain unobserved, never zero. An explicit complete three-day zero is a measured zero. Invalid responses or source failures while measuring feed leaders preserve the last accepted chart. Optional coverage has its own 20-second deadline; any failure discards its entire supplement and publishes the fully measured leaders, with the error and additional count logged by the CLI. Provider retry waits still apply when optional samples fail.

The registered job has payload `{}` and concurrency key `catalog.movies.popularity`, distinct from facts bootstrap's `catalog.movies` key. The worker runs the fixed `refresh-movie-popularity.js` CLI with a 150-second child limit. Run it locally with `pnpm --filter api catalog:movies:popularity`. Migration `0046_schedule_popularity_jobs` schedules unscheduled registrations daily at `50 5 * * *` UTC and enables the default, while preserving administrator-customized cron settings.

The official [Wikimedia pageview API](https://doc.wikimedia.org/generated-data-platform/aqs/analytics-api/reference/page-views.html) requires an identifying user agent and serial requests under its [access policy](https://doc.wikimedia.org/generated-data-platform/aqs/analytics-api/documentation/access-policy.html). The client uses `VefaLibrary/1.0 (+https://vefacaglar.com)`, fixed HTTPS origins, serial requests at least 500 ms apart, a 120-second total deadline, a 96-request ceiling, 15-second request timeouts and 2 MiB decoded response limits. No arbitrary URL or date is accepted in a job payload.

If yesterday's top feed is unavailable (404), at most two older completed days are tried, never before the accepted observation. The selected feed date is also the end of every three-day window. Exactly 1,000 article entries and their complete date/project/rank metadata are validated. Wikidata title lookups contain at most 50 titles and encoded URLs at most 6,500 characters. Every requested title must be accounted for through an explicit sitelink, alias or missing marker. Unexplained omissions fail the source. Multiple feed aliases for one QID select the highest-view article deterministically and do not add together.

Only QIDs already in the discovered movie catalog qualify. Unhydrated film stubs can receive measurements; hydrated entities known not to be films are excluded. The scoring job does not discover unrelated entities or hydrate facts. After complete validation, one short transaction locks popularity state, checks monotonic date progression, clears previous observations, stores the measured rolling scores in `movies.wikipedia_views`, and advances accepted metadata. `wikipedia_source_date` is the window end. Same-date replay is idempotent; older/future/current-day observations are rejected. Validated empty projections remain possible. The `movie_popularity_state` counters describe the candidate feed, and `observed_movie_count` describes measured catalog films.

The new source key is `enwiki-current-interest-v2`. The old `enwiki-top-articles-v1` diagnostic row is retained. Its one-day values cannot establish freshness for the new chart. The first refresh can measure the currently completed window even when the old source already accepted that end date. An outstanding legacy AQS cooldown is carried into the new source row. No database migration is needed. Deploy the API and worker together, then run the popularity job and dedicated `search.movies.sync` job. Movie search schema 4 gates old publications and rebuilds safely; SQL serves the catalog during the transition.

AQS failures and cooldowns live in the source's `movie_popularity_state` row. Wikidata mapping failures extend the shared facts cooldown with `GREATEST` without changing its discovery cursor, revision or failure counter. Provider `Retry-After` is respected. Delayed/cooldown attempts never renew the accepted date. Failed optional measurements are visible in job output and do not renew or replace unmeasured films with invented values.

Public browsing orders fresh measured scores descending, then Wikipedia language coverage, title and ID. Unobserved films follow by language coverage, title and ID. When no public film has a current observation, or the source window is stale/absent, the descriptor uses `recognition` and the page explicitly labels language coverage. The date is fresh only when it is a completed UTC day within seven days. The public descriptor is `{mode, sourceDate, sourceUrl, isFresh, windowDays}` (`windowDays = 3` for this source), with the source link pointing to Wikimedia's metric documentation. Numeric measurements are not added to public cards. Typed search keeps relevance first and uses the existing interest/recognition tie-break contract.

The dedicated Meilisearch movie publication serves the same browse order after the complete ranking generation is synchronized. PostgreSQL remains canonical for cards and the fallback page/count/descriptor, captured in one statement snapshot. See [movie search](movie-search.md). Fresh measured stubs receive temporary priority in normal facts hydration without rewriting permanent seed priority or retry counters. Facts snapshots preserve independent observation columns.
