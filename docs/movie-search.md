# Public movie search

`GET /api/movies` uses Typesense for browsing, typed search, ordering, counts and pagination when the dedicated movie publication is ready. `GET /api/movies/people/:wikidataId` uses the same index with an exact person-QID filter. PostgreSQL remains canonical for person headers, movie details, current poster attribution/safety checks, and the selected page's role labels. The index stores only IDs, titles, distinct nondeprecated credited person QIDs, interest scores and sort keys. English catalog source data is shared across request languages.

`MovieCatalogService` reads `movie_search_state` before the search and again after card hydration. Both reads must identify the same ready physical collection, schema version, ranking generation and published source date. No readiness state is cached across requests. Missing/unready metadata, an unavailable index, a failed/partial search page, a changed publication or a film that is no longer public/person-linked falls back to the existing SQL query. A successful ready search with zero matches stays empty. Known people with empty filmographies remain 200; unknown people remain 404. Out-of-range pages retain their real count and ranking descriptor.

Typesense reads have a three-second response deadline and a thirty-second failure cooldown. Browse keeps `interestScore:desc,titleSort:asc,tieBreakId:asc` when current interest is fresh, or `titleSort:asc,tieBreakId:asc` otherwise. Typed searches instead use `_text_match:desc,interestRecognitionRank:desc,tieBreakId:asc`, or `_text_match:desc,recognitionCount:desc,tieBreakId:asc` when interest is stale/absent. Titles and original titles have equal weights, `max_score` preserves alternate-title matches, and token-position priority favors titles beginning with the query. Exact whole-field priority and matching-field-count priority are disabled: an obscure film named exactly “Star Wars” must not automatically outrank the related main films, and duplicate title/original-title text must not earn an extra boost. No franchise-specific overrides or broad text-score buckets are used.

Recognition is the number of distinct Wikipedia language-edition hosts in a complete Wikidata sitelink snapshot, excluding Wikimedia Commons, Wikispecies, Wikiquote and other sibling projects. It is a general recognition proxy, not a user rating, a franchise membership assertion or current popularity. Canonical `wikipedia_language_count` is nullable until enrichment; an explicitly empty complete snapshot stores zero. Both map to zero in the index. Count values are bounded to `[0, 1000000)`. For fresh ranking, `interestRecognitionRank = (interestScore + 1) * 1000000 + recognitionCount` retains interest before recognition within equally relevant matches and fits both PostgreSQL int64 and JavaScript safe integers for every int32 interest value. Multiplication casts to bigint first. Unobserved interest is `-1`, distinct from observed zero. Freshness follows the existing completed UTC day/seven-day rule at request time. UUID is always the final deterministic tie-breaker, within Typesense's three-sort-field limit.

String sort keys explicitly enable `sort: true`. Typesense string sorting and PostgreSQL locale collation can differ for accents and punctuation, so fallback order is not promised to be byte-for-byte identical. SQL fallback remains available during index outages or version transitions and does not implement Typesense relevance. The schema contract is `apps/api/src/modules/movies/search/movie-search.schema.json`. See the [Typesense sorting documentation](https://typesense.org/docs/29.0/api/search.html#ranking-and-sorting-parameters).

# Dedicated synchronization

Only `search.movies.sync` owns the `movies_en` alias and current `movies_en__v2_*` physical collections. Payload is `{}` and the concurrency key is `search.index`, shared with generic search jobs and game popularity indexing. Generic `search.reindex` and `search.sync` continue to own only their seven existing game/facet/post collections; they never create, synchronize or clean up movie collections.

Migration `0033_chunky_baron_strucker` creates `movie_search_state` and `movie_search_sync`, seeds the singleton state and registers `search.movies.sync` at `*/5 * * * *` UTC, initially **disabled**. Apply that migration before deploying API/worker code using the new tables. Once both deployments succeed, enable the registered job and run it once through the dashboard/API. Keep the existing movie fact and Wikipedia interest schedules intact. Run only this dedicated job to populate movies; a generic full reindex is unnecessary.

Migration `0036_mute_nova` adds the nullable canonical recognition count, its bound check and a partial backfill index. Apply it before deploying the API/worker using schema v2. A v1 active publication or unfinished v1 cursor starts a new v2 shadow from the beginning; the old physical collection and alias remain intact until the replacement is ready. The new API uses SQL fallback during that transition. Do not mark an old publication v2 manually or delete legacy collections as part of rollout.

Normal movie hydration now requests complete sitelinks with URLs in the same provider response. Equal Wikidata revisions still enrich changed recognition counts and queue their search revision, without overwriting the stored title/relationships. Before ordinary hydration/refresh, the existing catalog job spends at most half its movie capacity and half its spare request allowance on public films missing recognition, retaining capacity for new films and normal daily rotation. It does not move the normal refresh cursor for this phase, and existing global time/movie/request budgets and cooldowns still apply. Pending due enrichment participates in bounded continuation; unavailable rows wait for their normal retry. Existing watch history, comments and ratings are not indexed.

The worker creates a shadow collection and scans public films by UUID keyset in batches of 500, persisting progress across job IDs. Source documents and their captured ledger revisions come from one database snapshot. Network requests do not hold source or ledger row locks. Every import result is checked; missing/nonpublic documents are deleted idempotently. The worker acknowledges only the revision it read, so a concurrent source write remains pending. After the scan it replays pending revisions before publishing the alias and explicit readiness. A retry resumes the durable shadow/cursor, including a crash between the alias swap and database publication. A missing or incompatible collection requires a new shadow; document count alone never establishes readiness. Existing data remains available until replacement finishes.

Movie facts, visibility/credit changes, changed poster inputs even at an unchanged Wikidata revision, and successful poster persistence enqueue dirty revisions inside the same source transaction. Reference-person label refreshes need no index update because names are read from PostgreSQL. Wikipedia interest publication queues the union of old and new observed films and invalidates the ranking generation atomically; readers use SQL until that captured generation is drained and published ready. The ledger has no movie FK and retains acknowledged rows, allowing a bounded daily reconciliation to detect hard deletions or films made nonpublic outside the normal writer.

These source transactions also mark the enabled, scheduled `search.movies.sync` registration due and notify the worker on commit. The due time is a durable, coalesced request: it survives a lost notification or a worker restart. Before every claim the capable worker dispatches that registration, with a five-second idle poll as a fallback. Its recurring row is locked with `FOR NO KEY UPDATE` so a producer cannot lose a request racing dispatch, while continuation inserts can still check their recurring-job foreign key. API manual enqueue takes the same recurring lock before inserting its job and updating recurring metadata, preventing a recurring/job lock inversion with dispatch. A shared `search.index` conflict retains the due request until a job can be enqueued; the ordinary scheduler follows the same rule. Queued retry/backoff and bounded-continuation times are preserved. A request arriving while a job finishes can produce one harmless empty follow-up, but an empty run never requests another run by itself. Disabling the registration or making its cron null also disables automatic source-triggered dispatch; Run now remains available. The five-minute cron remains a reconciliation fallback, rather than the normal wait after a source update.

Runs are bounded and check cancellation between batches. A successor is allowed only after committed progress with remaining work, at least thirty seconds later; an ordinary empty run succeeds without a continuation. Cancelled/failed batches preserve durable markers for the next explicit/scheduled retry. This remains eventual consistency: an idle worker normally starts after the commit notification, while another search job, retry delay, outage or bounded synchronization window can delay publication. A committed source write does not wait for remote Typesense availability. Canonical card hydration prevents stale indexed documents from leaking nonpublic film cards, but successful no-match results do not invoke SQL to discover newly added films.

For recovery, inspect the registered job's logs/progress and `movie_search_state` (phase, active/building collections, cursor, ranking generation/readiness, repair markers) plus pending ledger revisions. Retry the dedicated job after fixing its configuration/provider error. Do not mark readiness manually from a nonzero collection count, delete unrelated collections or truncate the ledger. Validate the completed publication with movie browse, a typed title query, a person filmography, a zero-match query, and the current poster metadata before considering rollout complete.
