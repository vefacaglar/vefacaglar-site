# Public movie search

`GET /api/movies` uses Meilisearch for browsing, typed search, ordering, counts and pagination when the dedicated movie publication is ready. `GET /api/movies/people/:wikidataId` uses the same index with an exact person-QID filter. PostgreSQL remains canonical for person headers, movie details, card hydration (with `posterImageUrl` and `posterAttribution` suppressed to `null`), and the selected page's role labels. The index stores only IDs, titles, distinct nondeprecated credited person QIDs, interest scores and sort keys. English catalog source data is shared across request languages.

`MovieCatalogService` reads `movie_search_state` before the search and again after card hydration. Both reads must show the ready `movies_en` index, schema version 4, the same ranking generation and the same published source date. No readiness state is cached across requests. Missing/unready metadata, an unavailable index, a failed/partial search page, a changed publication or a film that is no longer public/person-linked falls back to the existing SQL query. A successful ready search with zero matches stays empty. Known people with empty filmographies remain 200; unknown people remain 404. Out-of-range pages retain their real count and ranking descriptor.

Meilisearch reads have a three-second response deadline and a thirty-second failure cooldown. Browse (an empty query) sorts by `interestScore:desc,recognitionCount:desc,titleSort:asc,tieBreakId:asc` when current interest is fresh, or `recognitionCount:desc,titleSort:asc,tieBreakId:asc` otherwise. Typed searches rank by relevance first (`words`, `typo`, `proximity`, `wordPosition`) and use `interestRecognitionRank:desc,tieBreakId:asc`, or `recognitionCount:desc,tieBreakId:asc` when interest is stale/absent, only to break ties. Titles and original titles have equal weights (no attribute ranking rule), so alternate-title matches are kept, and word position favors titles beginning with the query. The `exactness` rule is left out: an obscure film named exactly “Star Wars” must not automatically outrank the related main films. No franchise-specific overrides or broad text-score buckets are used.

Fresh movie interest scores are the normalized, recency-weighted mean of three complete human-view days described in [movie interest](movie-interest.md). Interest is available only when the source date is current and at least one public film has a measurement for that date. A source transition uses the new source-state key, so legacy one-day observations cannot qualify.

Recognition is the number of distinct Wikipedia language-edition hosts in a complete Wikidata sitelink snapshot, excluding Wikimedia Commons, Wikispecies, Wikiquote and other sibling projects. It is a general recognition proxy, not a user rating, a franchise membership assertion or current popularity. Canonical `wikipedia_language_count` is nullable until enrichment; an explicitly empty complete snapshot stores zero. Both map to zero in the index. Count values are bounded to `[0, 1000000)`. For fresh ranking, `interestRecognitionRank = (interestScore + 1) * 1000000 + recognitionCount` retains interest before recognition within equally relevant matches and fits both PostgreSQL int64 and JavaScript safe integers for every int32 interest value. Multiplication casts to bigint first. Unobserved interest is `-1`, distinct from observed zero. Freshness follows the existing completed UTC day/seven-day rule at request time. UUID is always the final deterministic tie-breaker.

Meilisearch string sorting and PostgreSQL locale collation can differ for accents and punctuation, so fallback order is not promised to be byte-for-byte identical. SQL fallback remains available during index outages or version transitions and does not implement Meilisearch relevance. The settings contract is `apps/worker/src/jobs/search/meili/movies_en.json`; see [search-meilisearch.md](search-meilisearch.md).

# Dedicated synchronization

Only `search.movies.sync` owns the `movies_en` index and its `movies_en__build_*` rebuild indexes. Payload is `{}` and the concurrency key is `search.movies.index`, allowing independent game indexing to run concurrently. Generic `search.reindex` and `search.sync` own only their seven game/facet/post indexes; they never create, synchronize or clean up movie indexes.

Migration `0047_free_dorian_gray` changes the original five-minute cron to daily `50 7 * * *` UTC (10:50 in Istanbul), preserving customized schedules and enabled status. Existing source rows stay dirty until the next daily run or a manual Run now. Run only this dedicated job to populate movies; a generic full reindex is unnecessary.

Schema version 4 is the Meilisearch publication. A state left by the Typesense deployment (schema 2, a `movies_en__v2_*` collection name) starts a fresh v4 build from the beginning; the API uses SQL fallback until it is ready. Do not mark an old publication v4 manually. Migration `0036_mute_nova` added the nullable canonical recognition count, its bound check and a partial backfill index.

Normal movie hydration now requests complete sitelinks with URLs in the same provider response. Equal Wikidata revisions still enrich changed recognition counts and queue their search revision, without overwriting the stored title/relationships. Before ordinary hydration/refresh, the existing catalog job spends at most half its movie capacity and half its spare request allowance on public films missing recognition, retaining capacity for new films and normal daily rotation. It does not move the normal refresh cursor for this phase, and existing global time/movie/request budgets and cooldowns still apply. Pending due enrichment participates in bounded continuation; unavailable rows wait for their normal retry. Existing watch history, comments and ratings are not indexed.

The worker creates `movies_en__build_<id>` with the settings file and scans public films by UUID keyset in batches of 500, persisting progress across job IDs (phase `scan`). Source documents and their captured ledger revisions come from one database snapshot. Network requests do not hold source or ledger row locks. Every document task is checked; missing/nonpublic documents are deleted idempotently. The worker acknowledges only the revision it read, so a concurrent source write remains pending. After the scan it replays pending revisions (phase `replay`). Then it commits phase `swap`, swaps the build with `movies_en` (renaming it in on the first build) and records the swap: `active_collection = 'movies_en'`, `bootstrap_phase = 'ready'`, `ranking_ready = false`, `ranking_generation + 1`. The same run drains revisions that arrived meanwhile and publishes readiness (`ranking_ready = true`). The old documents, now in the build index, are deleted. A retry resumes the durable build/cursor; a crash after phase `swap` finishes the swap without a second swap or rescan (Meilisearch's task history shows whether it already happened). A missing index or outdated settings require a new build; document count alone never establishes readiness. Existing data remains available until the replacement finishes.

Movie facts, visibility/credit changes, and source-claim input changes even at an unchanged Wikidata revision enqueue dirty revisions inside the same source transaction. Reference-person label refreshes need no index update because names are read from PostgreSQL. Wikipedia interest publication queues the union of old and new observed films and invalidates the ranking generation atomically; readers use SQL until that captured generation is drained and published ready. The ledger has no movie FK and retains acknowledged rows, allowing a bounded daily reconciliation to detect hard deletions or films made nonpublic outside the normal writer.

Source transactions only persist dirty revisions. They do not change the recurring schedule or dispatch extra jobs. The ordinary scheduler starts one daily campaign, and Run now can start one manually. Large campaigns retain their bounded continuations and retries until complete. The dedicated `search.movies.index` lock suppresses duplicate schedule occurrences while the same movie campaign is already active. Independent game search jobs can run alongside it. The next daily time remains intact after completion.

Runs are bounded and check cancellation between batches. A successor is allowed only after committed progress with remaining work, at least thirty seconds later; an ordinary empty run succeeds without a continuation. Cancelled/failed batches preserve durable markers for the next explicit/scheduled retry. This remains eventual consistency: an idle worker normally starts after the commit notification, while another search job, retry delay, outage or bounded synchronization window can delay publication. A committed source write does not wait for remote Meilisearch availability. Canonical card hydration prevents stale indexed documents from leaking nonpublic film cards, but successful no-match results do not invoke SQL to discover newly added films.

For recovery, inspect the registered job's logs/progress and `movie_search_state` (phase, active/building index, cursor, ranking generation/readiness, repair markers) plus pending ledger revisions. Retry the dedicated job after fixing its configuration/provider error. Do not mark readiness manually from a nonzero document count, delete unrelated indexes or truncate the ledger. Validate the completed publication with movie browse, a typed title query, a person filmography, and a zero-match query before considering rollout complete.

## People index

`search.movies.sync` also owns the `movie_people_en` index (settings `apps/worker/src/jobs/search/meili/movie_people_en.json`, schema version 2). After the movie step, the same run rebuilds a full snapshot of searchable people — a non-blank name and at least one non-deprecated credit on a public film — keyed by `movie_people.id`, with `publicCreditCount` and `nameSort` for ranking. It loads `movie_people_en__build_<id>`; progress lives in `movie_people_search_state`, and the keyset cursor advances only after an imported batch. After a complete scan the build is swapped with `movie_people_en` and the state is published (`active_collection = 'movie_people_en'`, `previous_collection` always `NULL`); the swapped-out build is deleted. A crash between the swap and the publish only publishes on the next run. A published snapshot is rebuilt after 12 hours, so the people index can lag the catalog by up to about one day plus the rebuild time (new people are missing from index results until then; people who lost every public credit make that query fall back to SQL). A people-step failure is logged and never fails the movie step.

The API (`MoviePeopleSearchService`) queries `movie_people_en` for person IDs and hydrates them from PostgreSQL. It falls back to the SQL prefix search (`movie_people_name_search_idx`) when the index is not published, Meilisearch is disabled, cooling down, or fails, or when an indexed person is no longer public.
