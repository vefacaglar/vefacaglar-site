# Wikidata movie catalog

Movies use anonymous official Wikidata endpoints; no API key, account, payment or TMDB/IMDb scraping is involved. Structured Wikidata facts are CC0. This is a source-selected catalog of items directly classified as film (`P31=Q11424`), not a promise of every film or complete credits. A verified full direct-class discovery projection returned approximately 351,000 distinct IDs in November 2026. Related works classified only through subclasses can be absent.

The first synchronization hydrates The Godfather, The Dark Knight, The Shawshank Redemption, Pulp Fiction and The Fellowship of the Ring before bulk discovery. Discovery creates unpublished stubs in replayable batches; only a usable source title, validated classification and hydrated claims make a film public. Stable public slugs contain the Wikidata QID. A later source classification change can remove an item from public browsing. The public API uses the dedicated movie Typesense index for browsing/search (`GET /api/movies`, default 21 per page) and person film lists, with SQL fallback until a complete publication is ready. Details (`GET /api/movies/:slug`) and people remain canonical PostgreSQL data; see [movie search](movie-search.md) for synchronization and recovery. User logging, ratings and watch history are outside this feature.

Only selected claims are stored: original title, English/fallback label and description, release precision, runtime when explicitly expressed in minutes, validated IMDb `tt` identifier, genres, companies, and cast/director/producer assertions. Credit statement GUIDs, rank and qualifiers survive the import; one person may have several roles. Cast order and completeness are never invented. Multiple valid IMDb assertions or an identifier already owned by another QID are marked as a conflict, without merging films or aborting the rest of the batch. Unknown dates, runtimes and supporting labels stay nullable.

Cast, director and producer links open `/movies/people/:wikidataId`. The public `GET /api/movies/people/:wikidataId` endpoint returns the stored person's name and paginated public films, defaulting to 21 per page. Multiple credits or roles count as one film; deprecated statements are excluded and role labels are deduplicated for the current page. The filmography shares the main catalog's ranking. A known person with no public films has an empty catalog; an unknown ID returns 404. Names without a resolved label fall back to the stable Wikidata ID. These pages describe relationships already stored in this catalog, not complete biographies or career histories, and make no additional provider requests.

External movie poster fetching and public/admin poster hotlinking are disabled. `MovieSyncService` makes no outbound requests to Wikimedia Commons or English Wikipedia for poster artwork, and all public movie endpoints (`GET /api/movies`, `GET /api/movies/:slug`, `GET /api/movies/people/:wikidataId`, `GET /api/movies/users/:username/library`) as well as `GET /api/movies/dashboard/movies` suppress `posterImageUrl` and `posterAttribution` (`null`), even when legacy values exist in PostgreSQL.

Migration `0027_movies_catalog` creates the normalized tables/indexes and a disabled, manual-only registered job. Apply it using the existing Drizzle migrator after auditing pending history; no reset or `db:push`. The API and worker must contain this code before the registered job is run. The worker needs only the existing database configuration, Node runtime and compiled API package. The CLI is `pnpm --filter api catalog:movies`, compiled path `/app/apps/api/dist/scripts/sync-movies.js`; production population should use the registered `catalog.movies.sync` job with payload `{}` and concurrency key `catalog.movies`.

Historical migrations `0031_right_tyrannus`, `0032_tired_serpent_society`, and `0039_chubby_lenny_balinger` added nullable artwork columns, sitelink/category metadata, and upgraded a manual-only `catalog.movies.sync` registration to enabled `0 3 * * *` (03:00 UTC, 06:00 Istanbul). Those database columns remain in place non-destructively for schema compatibility while outbound artwork resolution and poster exposure are disabled. Apply migrations **before deploying the API/worker code that reads the columns**: from the release checkout, with the production `DATABASE_URL` already supplied securely, run `pnpm --filter @vefacaglar/db db:migrate`. API/worker deployment does not automatically run this command. Do not use `db:push` or expose the database URL in command arguments.

Each window is bounded to 150 seconds, 40 provider requests and 500 total movie hydration/refresh attempts by default. Entity and label requests contain at most 50 IDs, use a descriptive User-Agent/maxlag, and are serialized with a minimum 500 ms spacing. Entity bodies are capped at 24 MiB; discovery is capped at 48 MiB. Discovery uses one unordered complete projection, accepts completion only after validated EOF and durable callback inserts, and persists a daily discovery cycle marker. A partial cycle replays idempotently; already hydrated rows are never reset. Revision refresh reserves capacity during bootstrap, so existing films are not starved by new stubs. Once hydration catches up, spare movie capacity refreshes multiple batches instead of only 50 rows per successor.

Full validated claims replace scalar facts, relationship assertions, source revision and completion markers inside one movie transaction. Missing, partial, malformed or older responses preserve previous facts and receive a retry delay. Label requests are cached/batched separately; unresolved people or companies do not block a valid film. The label cache rotates both missing and known names after seven days. Character QIDs retained in source qualifiers resolve against this cache when details are read, so later labels are visible without a film revision change. Source failures persist a provider-wide Retry-After cooldown across new job IDs. Three consecutive failed windows exhaust automatic continuations; a later scheduled or manual run can retry. A run during an unchanged cooldown does not create another job.

Successful windows log a plain summary of whitelisted numeric counters for the dashboard, then emit exactly one `[catalog:movies] result` JSON line. Only `hasMore=true` plus `progressMade=true` permits the worker to atomically complete the current job and enqueue one successor, at least 30 seconds later (or at the provider cooldown). Cancellation/error/no-progress never creates a successor. This preserves FIFO fairness and registered-job linkage. Initial bootstrap requires many bounded windows; actual completion time depends on source responses and local database throughput. Verify a first successful job, its successor, rising discovered/hydrated counts, and public pages after deployment. Do not mark bootstrap complete merely because the seed films are visible.
