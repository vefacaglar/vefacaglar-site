# Wikidata movie catalog

Movies use anonymous official Wikidata endpoints; no API key, account, payment or TMDB/IMDb scraping is involved. Structured Wikidata facts are CC0. This is a source-selected catalog of items directly classified as film (`P31=Q11424`), not a promise of every film or complete credits. A verified full direct-class discovery projection returned approximately 351,000 distinct IDs in November 2026. Related works classified only through subclasses can be absent.

The first synchronization hydrates The Godfather, The Dark Knight, The Shawshank Redemption, Pulp Fiction and The Fellowship of the Ring before bulk discovery. Discovery creates unpublished stubs in replayable batches; only a usable source title, validated classification and hydrated claims make a film public. Stable public slugs contain the Wikidata QID. A later source classification change can remove an item from public browsing. The public API is SQL-backed (`GET /api/movies`, default 21 per page, indexed title prefix search; `GET /api/movies/:slug`). Movies do not use Typesense initially. User logging, ratings and watch history are outside this feature.

Only selected claims are stored: original title, English/fallback label and description, release precision, runtime when explicitly expressed in minutes, validated IMDb `tt` identifier, genres, companies, and cast/director/producer assertions. Credit statement GUIDs, rank and qualifiers survive the import; one person may have several roles. Cast order and completeness are never invented. Multiple valid IMDb assertions or an identifier already owned by another QID are marked as a conflict, without merging films or aborting the rest of the batch. Unknown dates, runtimes and supporting labels stay nullable. Image URLs remain null: a Wikidata image is not proof of a film poster or its reuse license.

Migration `0027_movies_catalog` creates the normalized tables/indexes and a disabled, manual-only registered job. Apply it using the existing Drizzle migrator after auditing pending history; no reset or `db:push`. The API and worker must contain this code before the registered job is run. The worker needs only the existing database configuration, Node runtime and compiled API package. The CLI is `pnpm --filter api catalog:movies`, compiled path `/app/apps/api/dist/scripts/sync-movies.js`; production population should use the registered `catalog.movies.sync` job with payload `{}` and concurrency key `catalog.movies`.

Each window is bounded to 150 seconds, 40 provider requests and 500 hydration attempts by default. Entity and label requests contain at most 50 IDs, use a descriptive User-Agent/maxlag, and are serialized with a minimum 500 ms spacing. Entity bodies are capped at 24 MiB; discovery is capped at 48 MiB. Discovery uses one unordered complete projection, accepts completion only after validated EOF and durable callback inserts, and persists a daily discovery cycle marker. A partial cycle replays idempotently; already hydrated rows are never reset. Revision refresh reserves capacity during bootstrap, so existing films are not starved by new stubs.

Full validated claims replace scalar facts, relationship assertions, source revision and completion markers inside one movie transaction. Missing, partial, malformed or older responses preserve previous facts and receive a retry delay. Label requests are cached/batched separately; unresolved people or companies do not block a valid film. Missing labels retry after seven days. Source failures persist a provider-wide Retry-After cooldown across new job IDs. Three consecutive failed windows exhaust automatic continuations; a later scheduled or manual run can retry. A run during an unchanged cooldown does not create another job.

Successful windows emit exactly one `[catalog:movies] result` JSON line. Only `hasMore=true` plus `progressMade=true` permits the worker to atomically complete the current job and enqueue one successor, at least 30 seconds later (or at the provider cooldown). Cancellation/error/no-progress never creates a successor. This preserves FIFO fairness and registered-job linkage. Initial bootstrap requires many bounded windows; actual completion time depends on Wikidata responses and local database throughput. Verify a first successful job, its successor, rising discovered/hydrated counts and public seed pages before enabling a daily recurring schedule. Do not mark bootstrap complete merely because the seed films are visible.
