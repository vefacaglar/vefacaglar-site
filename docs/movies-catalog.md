# Wikidata movie catalog

Movies use anonymous official Wikidata endpoints; no API key, account, payment or TMDB/IMDb scraping is involved. Structured Wikidata facts are CC0. This is a source-selected catalog of items directly classified as film (`P31=Q11424`), not a promise of every film or complete credits. A verified full direct-class discovery projection returned approximately 351,000 distinct IDs in November 2026. Related works classified only through subclasses can be absent.

The first synchronization hydrates The Godfather, The Dark Knight, The Shawshank Redemption, Pulp Fiction and The Fellowship of the Ring before bulk discovery. Discovery creates unpublished stubs in replayable batches; only a usable source title, validated classification and hydrated claims make a film public. Stable public slugs contain the Wikidata QID. A later source classification change can remove an item from public browsing. The public API is SQL-backed (`GET /api/movies`, default 21 per page, indexed title prefix search; `GET /api/movies/:slug`). Movies do not use Typesense initially. User logging, ratings and watch history are outside this feature.

Only selected claims are stored: original title, English/fallback label and description, release precision, runtime when explicitly expressed in minutes, validated IMDb `tt` identifier, genres, companies, and cast/director/producer assertions. Credit statement GUIDs, rank and qualifiers survive the import; one person may have several roles. Cast order and completeness are never invented. Multiple valid IMDb assertions or an identifier already owned by another QID are marked as a conflict, without merging films or aborting the rest of the batch. Unknown dates, runtimes and supporting labels stay nullable.

Posters use the explicit [Wikidata film-poster claim P3383](https://www.wikidata.org/wiki/Property:P3383), not P18 stills or a title search. The [Commons imageinfo API](https://www.mediawiki.org/wiki/API:Imageinfo) resolves five filenames per request, with at most 20 poster checks per window and the same total request/time budget. Only verified Wikimedia HTTPS thumbnails with a source page, plain-text creator credit and supported reuse terms (CC BY, CC BY-SA, CC0 or explicit public domain) are published. Cards and details show the creator, license and source link; source metadata HTML is never rendered. See [Commons reuse guidance](https://commons.wikimedia.org/wiki/Commons:Reusing_content_outside_Wikimedia). Free poster coverage is sparse, particularly for recent films, so missing artwork retains the placeholder. No API key is needed.

Artwork is checked independently of Wikidata revision equality. A refreshed existing film can acquire its first poster even when its source revision is unchanged. Changed/removed poster claims clear the previous image; authoritative missing or unsupported-license results are cached for 30 days, and accepted posters are rechecked after seven days. Provider outages preserve existing images, honor Retry-After and persist a separate Commons cooldown without blocking Wikidata discovery/content updates. Existing films acquire poster candidates as the bounded daily revision rotation reaches them; this is not an immediate full-catalog backfill.

Migration `0027_movies_catalog` creates the normalized tables/indexes and a disabled, manual-only registered job. Apply it using the existing Drizzle migrator after auditing pending history; no reset or `db:push`. The API and worker must contain this code before the registered job is run. The worker needs only the existing database configuration, Node runtime and compiled API package. The CLI is `pnpm --filter api catalog:movies`, compiled path `/app/apps/api/dist/scripts/sync-movies.js`; production population should use the registered `catalog.movies.sync` job with payload `{}` and concurrency key `catalog.movies`.

Migration `0031_right_tyrannus` adds nullable artwork storage and upgrades a manual-only `catalog.movies.sync` registration to enabled `0 3 * * *` (03:00 UTC, 06:00 Istanbul). Existing non-null cron expressions are preserved. The dashboard's Registered tab displays/edits UTC schedules and can change or clear the daily default. This job discovers new films, refreshes stale content, and resolves poster artwork in bounded successor windows; it does not guarantee every film changes daily. Apply migrations **before deploying the API/worker code that reads the new columns**: from the release checkout, with the production `DATABASE_URL` already supplied securely, run `pnpm --filter @vefacaglar/db db:migrate`. API/worker deployment does not automatically run this command. Do not use `db:push` or expose the database URL in command arguments.

Each window is bounded to 150 seconds, 40 provider requests and 500 total movie hydration/refresh attempts by default. Entity and label requests contain at most 50 IDs, use a descriptive User-Agent/maxlag, and are serialized with a minimum 500 ms spacing. Entity bodies are capped at 24 MiB; discovery is capped at 48 MiB; Commons bodies at 4 MiB with one-second request spacing. Discovery uses one unordered complete projection, accepts completion only after validated EOF and durable callback inserts, and persists a daily discovery cycle marker. A partial cycle replays idempotently; already hydrated rows are never reset. Revision refresh reserves capacity during bootstrap, so existing films are not starved by new stubs. Once hydration catches up, spare movie capacity refreshes multiple batches instead of only 50 rows per successor.

Full validated claims replace scalar facts, relationship assertions, source revision and completion markers inside one movie transaction. Missing, partial, malformed or older responses preserve previous facts and receive a retry delay. Label requests are cached/batched separately; unresolved people or companies do not block a valid film. The label cache rotates both missing and known names after seven days. Character QIDs retained in source qualifiers resolve against this cache when details are read, so later labels are visible without a film revision change. Source failures persist a provider-wide Retry-After cooldown across new job IDs. Three consecutive failed windows exhaust automatic continuations; a later scheduled or manual run can retry. A run during an unchanged cooldown does not create another job.

Successful windows log a plain summary of whitelisted numeric counters, including poster checks/updates/failures, for the dashboard, then emit exactly one `[catalog:movies] result` JSON line. Only `hasMore=true` plus `progressMade=true` permits the worker to atomically complete the current job and enqueue one successor, at least 30 seconds later (or at the provider cooldown). Cancellation/error/no-progress never creates a successor. This preserves FIFO fairness and registered-job linkage. Initial bootstrap requires many bounded windows; actual completion time depends on source responses and local database throughput. Verify a first successful job, its successor, rising discovered/hydrated counts, poster counters and public pages after deployment. Do not mark bootstrap complete merely because the seed films are visible.
