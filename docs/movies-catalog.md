# Wikidata movie catalog

Movies use anonymous official Wikidata endpoints; no API key, account, payment or TMDB/IMDb scraping is involved. Structured Wikidata facts are CC0. This is a source-selected catalog of items directly classified as film (`P31=Q11424`), not a promise of every film or complete credits. A verified full direct-class discovery projection returned approximately 351,000 distinct IDs in November 2026. Related works classified only through subclasses can be absent.

The first synchronization hydrates The Godfather, The Dark Knight, The Shawshank Redemption, Pulp Fiction and The Fellowship of the Ring before bulk discovery. Discovery creates unpublished stubs in replayable batches; only a usable source title, validated classification and hydrated claims make a film public. Stable public slugs contain the Wikidata QID. A later source classification change can remove an item from public browsing. The public API uses the dedicated movie Typesense index for browsing/search (`GET /api/movies`, default 21 per page) and person film lists, with SQL fallback until a complete publication is ready. Details (`GET /api/movies/:slug`), poster projection and people remain canonical PostgreSQL data; see [movie search](movie-search.md) for synchronization and recovery. User logging, ratings and watch history are outside this feature.

Only selected claims are stored: original title, English/fallback label and description, release precision, runtime when explicitly expressed in minutes, validated IMDb `tt` identifier, genres, companies, and cast/director/producer assertions. Credit statement GUIDs, rank and qualifiers survive the import; one person may have several roles. Cast order and completeness are never invented. Multiple valid IMDb assertions or an identifier already owned by another QID are marked as a conflict, without merging films or aborting the rest of the batch. Unknown dates, runtimes and supporting labels stay nullable.

Cast, director and producer links open `/movies/people/:wikidataId`. The public `GET /api/movies/people/:wikidataId` endpoint returns the stored person's name and paginated public films, defaulting to 21 per page. Multiple credits or roles count as one film; deprecated statements are excluded and role labels are deduplicated for the current page. The filmography shares the main catalog's ranking and poster safeguards. A known person with no public films has an empty catalog; an unknown ID returns 404. Names without a resolved label fall back to the stable Wikidata ID. These pages describe relationships already stored in this catalog, not complete biographies or career histories, and make no additional provider requests.

Posters prefer the explicit [Wikidata film-poster claim P3383](https://www.wikidata.org/wiki/Property:P3383), not P18 stills or a title search. The [Commons imageinfo API](https://www.mediawiki.org/wiki/API:Imageinfo) resolves five filenames per request. Commons images still require verified Wikimedia HTTPS thumbnails, a source page, plain-text creator credit and supported reuse terms (CC BY, CC BY-SA, CC0 or explicit public domain). See [Commons reuse guidance](https://commons.wikimedia.org/wiki/Commons:Reusing_content_outside_Wikimedia). No API key is needed.

When Commons has no usable poster, an exact English Wikipedia sitelink supplies a fallback. [PageImages](https://www.mediawiki.org/wiki/Extension:PageImages#API) is requested with `pilicense=any`; the returned article must have the same Wikidata QID, and the selected file must have explicit film-poster metadata categories. Stills, logos, arbitrary P18 images and title guesses are rejected. Article resolution and file metadata are separate batched requests, both counted against the same job budget. Only official Wikimedia image hosts and Wikipedia/Commons file source pages are accepted.

Wikipedia frequently identifies these files as non-free and provides no creator. Such artwork is labeled **Wikipedia · Non-free poster**, with its source file link; creators or license links are not invented. Wikipedia's source-specific fair-use rationale is not a general reuse license. Reusable artwork retains its actual creator/license attribution, including legacy Commons rows saved before provider metadata was added. Source metadata HTML is never rendered.

Artwork is checked independently of Wikidata revision equality. A durable priority pass bootstraps exact sitelinks for seed films and films in the current public order, even when recently checked, before the larger catalog rotation. Public sorting is unchanged. Complete responses with no enwiki article are recorded once rather than repeatedly occupying the priority pass. Changed source inputs advance a compare-and-swap version; late artwork responses cannot overwrite a newer candidate. P3383 remains separate from the resolved Wikipedia filename, and absent/unchanged P3383 does not erase a valid Wikipedia poster. Authoritative missing/unverified artwork is cached for 30 days, accepted posters for seven days. Transient errors preserve valid artwork, honor Retry-After and use independent Commons/Wikipedia cooldowns without stopping movie discovery/content updates. At most 20 films are considered for artwork per bounded window; population is gradual across the catalog.

For the Wikipedia fallback rollout, apply the migration first, then complete the new API and web deployments before allowing the new worker to write Wikipedia poster rows. The API, web and worker workflows deploy independently, so hold the worker deployment until the API and web deployments have succeeded. The previous API cannot serialize the nullable creator and license URL in non-free Wikipedia poster metadata and returns HTTP 500 for affected movies. Once those rows exist, do not roll the API back alone to a version from before the fallback.

Each window is bounded to 150 seconds, 40 provider requests and 500 total movie hydration/refresh attempts by default. Entity and label requests contain at most 50 IDs, use a descriptive User-Agent/maxlag, and are serialized with a minimum 500 ms spacing. Entity bodies are capped at 24 MiB; discovery is capped at 48 MiB; Commons and Wikipedia artwork bodies at 4 MiB with one-second request spacing per provider. Discovery uses one unordered complete projection, accepts completion only after validated EOF and durable callback inserts, and persists a daily discovery cycle marker. A partial cycle replays idempotently; already hydrated rows are never reset. Revision refresh reserves capacity during bootstrap, so existing films are not starved by new stubs. Once hydration catches up, spare movie capacity refreshes multiple batches instead of only 50 rows per successor.

Full validated claims replace scalar facts, relationship assertions, source revision and completion markers inside one movie transaction. Missing, partial, malformed or older responses preserve previous facts and receive a retry delay. Label requests are cached/batched separately; unresolved people or companies do not block a valid film. The label cache rotates both missing and known names after seven days. Character QIDs retained in source qualifiers resolve against this cache when details are read, so later labels are visible without a film revision change. Source failures persist a provider-wide Retry-After cooldown across new job IDs. Three consecutive failed windows exhaust automatic continuations; a later scheduled or manual run can retry. A run during an unchanged cooldown does not create another job.

Successful windows log a plain summary of whitelisted numeric counters, including poster checks/updates/failures, for the dashboard, then emit exactly one `[catalog:movies] result` JSON line. Only `hasMore=true` plus `progressMade=true` permits the worker to atomically complete the current job and enqueue one successor, at least 30 seconds later (or at the provider cooldown). Cancellation/error/no-progress never creates a successor. This preserves FIFO fairness and registered-job linkage. Initial bootstrap requires many bounded windows; actual completion time depends on source responses and local database throughput. Verify a first successful job, its successor, rising discovered/hydrated counts, poster counters and public pages after deployment. Do not mark bootstrap complete merely because the seed films are visible.
