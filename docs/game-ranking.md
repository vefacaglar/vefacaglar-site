# Game catalog ranking

The default public `/explore/games` list ranks current interest from IGDB. Verified single-player support adds a small relative preference. Card review scores, private ratings, user logs, and playtime do not affect ordering.

The daily `catalog.popularity.refresh` job reads IGDB Visits (70%), Playing (20%), and Steam 24-hour peak players (10%). Every signal is divided by its current global provider peak and square-rooted before blending. This preserves audience-size differences while softening extreme peaks. A game with only Steam activity can contribute at most the Steam weight, even when its other measurements are unavailable. Only observations with a `calculated_at` within the last 72 hours are accepted, with five minutes of future clock tolerance. Undated, stale, or invalid observations do not enter discovery or scoring. Missing measurements remain unknown; a game with no valid measurements keeps a null score. Lifetime rating and review totals do not enter this calculation.

Single-player games receive at most a 5% relative boost to the blend. The final score is divided by 1.05 to keep the stored range at 0–1. This can reorder games with close interest scores, while a larger popularity gap wins. Unknown modes receive no bonus. A zero or missing interest score cannot gain an independent preference score. Genres do not affect public ranking.

The job stores this final value in `games.popularity_score`, the canonical public/API/search score. Each score is dated with its own oldest contributing provider observation in `popularity_updated_at`. After 72 hours, SQL public cards expose a null score and browsing falls back to title/UUID for those games, even if the job has stopped running. A marginal observation affects only its own game. SQL browsing and company pages order current scores descending, then title and UUID. Existing owner-taste recommendation fields remain available to administrative diagnostics and do not control the public list. Publishing the new API immediately removes their influence on SQL browsing; running the normal popularity job recomputes every IGDB-linked game's canonical score and synchronizes search. Typed searches retain title relevance, including exact/prefix priority in the SQL fallback.

Before scoring, the refresh discovers missing leaders from the top 200 current Visits games, top 50 Playing games, and top 50 Steam activity games. It fetches at most 300 explicit IDs in one bounded request and passes eligible main games, remakes, remasters, expanded games, and standalone expansions through the existing canonical importer. Eligibility follows game type and excludes editions via `version_parent`. A remake may reference its original through `parent_game` and remains eligible. DLC, mods, and other unsupported game types are excluded. Existing content is only filled where missing, and known IGDB identities are skipped. Newly imported games participate in the same refresh. Discovery failures fail the job before replacing the last good scores, allowing an ordinary retry. This bounded pass complements the resumable `catalog:import --all` CLI.

Game-mode hydration uses explicit IGDB IDs in batches of at most 500, at most 20 batches / 30 seconds per refresh, sharing the client's request spacing below 4 requests/second. All unchecked/stale IGDB games are eligible in current-interest/UUID keyset order, across all genres. Successful lookups age out after 90 days, so later runs rotate through remaining candidates. A valid response omitting a game records the attempt age but retains its unknown or previously known modes. Failed or malformed batches do not change lookup state. Provider unavailability is reported separately and does not prevent interest refresh; database errors fail the job.

Public developer and publisher pages use `/explore/games/developers/:slug` and `/explore/games/publishers/:slug`. Each page lists the games connected to that role using the same SQL order and public card fields. Association `EXISTS` filters keep game counts and pagination independent of join fan-out. The dedicated anonymous API features are under `/api/games`; administrative catalog routes remain protected.

This ranking update requires no new migration, credential, or recurring job type. Deploy the API and worker, then run the registered `catalog.popularity.refresh` job. Strict CLI runs synchronize all considered games into search, so a retry also repairs an earlier failed index write. Mode coverage fills over bounded runs; an initial refresh does not imply that every game has verified modes.
